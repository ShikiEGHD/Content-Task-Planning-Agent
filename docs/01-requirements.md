# 01 需求与验收标准

## 文档状态与来源

依据用户提供的三张考题截图整理。截图为需求来源；本轮任务是建立目录与路线，不是在本轮声称完成考题。用户在对话中确认 Python、LangGraph、CLI、云端 API 与离线 Mock。其余设计为待确认建议。

## 用户、目标与输入输出

用户：内容活动运营人员。

目标：在预算与截止时间内完成一份内容活动方案；不能完成时返回原因和缺口，并保留已成功步骤的结果。

输入：主题、预算、截止时间。材料：合成素材、工具费用与耗时表。工具：素材检索、脚本生成、成本估算、方案保存。

输出：任务计划、步骤状态、工具结果、费用明细与合计、已保存方案或未完成原因。

## 范围与限制

- 建议投入约 3 小时，优先实现核心链路，记录实际耗时与未完成部分。
- 界面、线上部署、多 Agent、生产级 Runtime 均不是必需。
- 语言、模型、框架自由选择，框架名称不加分，技术取舍和修改结果应可解释。
- CLI、HTTP API、Notebook 三选一；本项目已选 CLI。
- 工具允许使用本地函数或 Mock。
- 模型不可用时保留离线 Mock 入口并说明边界；Mock 仅验证流程。
- 运行命令或步骤必须可复制；截图、视频不能替代代码。
- 示例仓库只能参考目录、文档、离线运行，不视为真实 ReAct 达标依据。

## Agent 决策硬性要求

至少实现模型选择动作、执行工具、观察结果、模型调整下一步或结束的循环。允许预设执行骨架，但固定条件分支、自动重试、预写日志不算满足动态决策。

提供至少两条执行路径，展示模型根据不同工具返回结果调整动作。记录步骤、工具参数、返回摘要、后续动作与简要决策依据，无需提交内部思维过程。

设置执行步数或工具调用次数上限，达到上限必须返回明确的未完成状态。

## 必须验收与扩展验证

| 编号 | 场景 | 成功标准 |
|---|---|---|
| R01 | 正常完成 | 方案保存成功，预算、时间、依赖和步骤状态一致 |
| R02 | 缺预算 | 标明缺失预算，不擅自补值，不保存为成功方案 |
| R03 | 缺截止时间 | 标明缺失截止时间，不擅自补值 |
| R04 | 工具失败 | 失败保留为失败，模型观察后调整行动或停止，保留成功结果 |
| R05 | 预算超限 | 重新规划并复核可行方案，或明确报告未完成与缺口 |
| R06 | 重复执行 | 结果和副作用可核对，不重复保存或重复计算已发生费用 |
| R07 | 步数/调用上限 | 达到上限后终止，返回未完成及已有结果 |
| R08 | 信息或资料不足 | 识别缺失素材/约束，不伪造成功，适当调整或停止 |
| R09 | 截止时间不可达 | 返回替代计划或时间缺口，不超时后仍标为完成 |
| R10 | 动态决策证据 | 至少两条真实模型路径，体现工具结果改变后续动作 |

R01—R06 对应项目必须验收；R07 来自通用 Agent 上限要求；R08 对应验证材料要求；R09 用于核验业务目标；R10 对应动态决策要求。

失败步骤续跑属于加分项。最小版本仍需在同一次执行中保留已成功结果；跨进程恢复应单列支持边界。

## 成功判断

只有必填信息齐全、所需依赖成功、最终估算有效且符合预算与截止时间、保存工具真实成功时，任务才可记为 completed。字段名和状态枚举在实现阶段确定。

不满足条件时明确区分需要补充信息、执行失败、无可行方案、达到上限等原因；内部简化为 incomplete 也须附具体原因。

## GitHub 交付要求

- README：环境、安装、运行、评审入口。
- src/：项目代码与模型/工具接入。
- tests/：可执行测试。
- examples/：输入、实际输出、Trace、测试结果。
- data/：按需提供合成资料和规则。
- docs/01—05：需求、方案、评估、AI 使用、复盘。
- 依赖文件与 .env.example；无配置时明确说明。
- 至少三组完整验证材料，覆盖正常、信息或资料不足、工具失败及全部验收点。
- 使用框架须注明版本、使用功能及承担的职责。
- 最终提交题号 2、GitHub URL、最终 commit SHA；私有仓库让指定评审账号可读。
- 所有材料位于同一仓库，不提交真实密钥或隐私数据。
