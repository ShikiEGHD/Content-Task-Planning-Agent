## 2. 最小可交付目标

实现一个单 Agent，使用四个本地业务工具，在预算与截止时间内完成内容活动方案：

1. 读取并校验主题、预算、截止时间。
2. LangGraph 中的模型节点选择下一动作。
3. 执行素材检索、脚本生成、成本估算或方案保存工具。
4. 把工具真实返回结果和当前状态送回模型。
5. 模型根据成本超限、错误或部分成功调整方案、选择替代工具参数或结束。
6. 成功时保存方案；无法完成或达到上限时返回明确原因和已有结果。

最小范围不要求界面、线上部署、多 Agent、向量数据库或生产级 Runtime。

至少留存两条真实模型执行路径：正常完成、以及超预算/工具失败后调整。离线 Mock 另外验证流程与边界。

## 3. LangGraph 执行设计草案

建议图结构：

```text
START
  ↓
输入校验 ── 缺少必要字段 ──→ 生成未完成结果 → END
  ↓
模型选择动作 ←──────────────┐
  ↓                       │
受控工具执行 → 更新状态/记录 ┘
  ↓
模型选择结束 → 终态校验 → 最终结果 → END
```

另设贯穿执行的步数、工具调用上限与异常终止。输入检查、工具参数检查、预算/时间守卫属于确定性控制；选择新方案、替代动作或主动停止由模型完成。

必须确保工具结果真实进入下一次模型上下文，不能用固定 if 分支或脚本输出冒充模型重规划。LangGraph 负责状态传递、节点与路由，业务代码负责费用、依赖、幂等和校验。

### 状态建议

- task_id、run_id、模式、主题、预算、截止时间和时区。
- 当前计划及版本、步骤依赖、每一步实际状态。
- 素材、脚本、已验证估算与已保存结果。
- 最近工具返回、错误、模型选择的动作及简短决策依据。
- 已发生费用、最终方案估算、预计完成时间。
- 已执行步数、工具调用次数、配置上限。
- 最终状态、未完成原因与缺口。

建议步骤状态：pending、running、succeeded、failed、skipped。最终状态至少能表达 completed 和 incomplete，并附具体原因；是否单列 needs_input/failed 等在实现前确定。

计划变更后关联估算必须失效并重新计算；工具失败不得记为成功；成功结果根据依赖保留或明确失效，不能静默丢失。

## 4. 四个工具的最小契约

| 工具 | 输入 | 返回结果 | 关键边界 |
|---|---|---|---|
| search_materials | 主题、条件 | 素材 ID、内容、可用性、替代素材 | 无结果/部分结果需明确返回 |
| generate_script | 素材 ID、内容形式、数量 | 脚本内容、使用素材与形式 | 支持可控故障，不能伪造成功 |
| estimate_cost | 当前方案、费用表、时间规则 | 费用明细、总额、工期、可行性 | 金额和时间由程序计算 |
| save_plan | 通过校验的方案、task_id/版本 | 保存路径、标识、真实保存状态 | 幂等、前置依赖检查、拒绝不可行方案 |

四个工具已按上述契约实现，字段由 dataclass/手动校验和云端原生 tool schema 双重约束。

预算核算要先约定：
- 初始报价 12、替代报价 8 是两份估算，不能算作花了 20。
- 真正执行工具产生的成本按费用规则累计；失败调用是否收费必须明确。
- 最终可行性应覆盖已发生费用与剩余待执行费用，不能重复计算已经发生的同一费用。
- 若修改方案复用已有素材或脚本，应说明费用及耗时如何复用。
- 云端模型费用单独说明是否纳入业务模拟预算；默认不擅自混合两种单位。

时间使用明确时区和固定测试时钟；依赖批次串行累计，独立脚本真实并发，模拟工期按并发槽排程，保留失败和重规划分钟。不用 sleep 模拟业务。计算公式见方案 v2。

## 5. 待用户选择的实现方法

### 5.1 云端模型与工具调用

已确定 DeepSeek 官方 API，使用 OpenAI Python SDK 直连，决策和脚本生成默认使用 `deepseek-flash`，并关闭思考模式。真实 API 验证需要本地密钥。

| 方法 | 优点 | 缺点 |
|---|---|---|
| 供应商官方 SDK/原生工具调用 | 原生能力和错误信息完整，工具结构约束通常较清晰 | 对供应商接口耦合较高 |
| 兼容接口 + 薄适配器 | 更换兼容供应商较方便，接口统一 | 兼容性和工具调用细节需实测 |
| 模型输出结构化 JSON 动作 | 可适配不支持原生工具调用的接口 | 需要严格校验与格式错误处理，可靠性需验证 |

建议在模型层定义统一决策接口，让 cloud 和 mock 返回相同动作结构。是否引入 LangChain 模型包装器另行比较：接入方便但增加依赖；直接 SDK 依赖较少但需要自行适配消息。

### 5.2 LangGraph 路由与工具执行

| 方法 | 优点 | 缺点 |
|---|---|---|
| 通用模型节点 + 受控工具分发节点（建议优先比较） | 代码较集中，便于保存守卫、计数和 Trace | 需自行做好分发与参数校验 |
| 每个业务工具使用独立图节点 | 依赖与步骤表现清晰 | 节点/路由更多，易写成固定流程 |

无论哪种方法，路由都应接受模型选择，程序只做合法性和安全边界校验。不要为每个测试场景硬编码一条完成路径。

### 5.3 脚本生成工具

| 方法 | 优点 | 缺点 |
|---|---|---|
| 本地模板/合成生成（建议最小版本比较） | 可离线、费用耗时可控，故障易复现 | 内容质量有限，需声明为模拟业务工具 |
| 调用生成模型 | 更接近真实内容业务 | 增加调用成本、网络依赖和失败点 |

本地模板业务工具是允许的；决策模型仍需真实云端调用取证。

### 5.4 重复执行与持久化

| 方法 | 优点 | 缺点 |
|---|---|---|
| 本地 JSON + 幂等索引（建议最小版本比较） | 直观、依赖少，易检查保存结果 | 原子写入、并发与索引一致性需处理 |
| SQLite | 标准库可用，唯一约束与事务方便 | 需要表结构和迁移约定 |
| LangGraph checkpointer + 业务幂等存储 | 适合图执行恢复，可争取续跑加分 | checkpoint 不自动解决业务副作用幂等，复杂度更高 |

同一次运行中保留成功结果属于核心要求；重复执行幂等也必须验收。跨进程从失败步骤续跑作为可选加分，不应挤占核心链路。

### 5.5 CLI、结构校验与测试

| 选择项 | 方法与优势 | 代价 |
|---|---|---|
| CLI | argparse：标准库、依赖少；Typer：参数帮助与命令组织便捷 | argparse 样板较多；Typer 增加依赖 |
| 结构校验 | dataclass/手动校验：轻量；Pydantic：结构与错误清晰 | 手写需自行保证完整性；Pydantic 增加依赖 |
| 测试 | pytest：参数化与夹具方便；unittest：标准库 | pytest 增加依赖；unittest 样板较多 |

当前没有替用户选定这些库。


## 8. 验证场景与证据

| 场景 | 预期行为 | 特别核验 |
|---|---|---|
| 正常完成 | 检索、生成、估算、保存 | 费用/耗时/依赖/状态一致 |
| 缺预算 | 返回需要补充信息 | 不默认猜值、不保存 |
| 缺截止时间 | 返回需要补充信息 | 与缺预算分别可测 |
| 资料不足 | 模型换检索条件、替代素材或停止 | 不编造工具结果 |
| 一次工具失败 | 模型选替代行动或停止 | 保留成功结果，失败不得成功化 |
| 预算 10、报价 12、替代 8 | 模型观察超限后修改方案并重估 | 由模型选择替代，记录实际结果 |
| 无可行方案 | 返回未完成与预算/时间缺口 | 不强行保存为成功 |
| 截止时间不可达 | 缩减方案或报告时间不足 | 固定时钟、带时区 |
| 同一 task_id 重复运行 | 复用已保存结果或明确版本策略 | 不重复保存/计费 |
| 达到上限 | 返回未完成与已有结果 | 不依赖无限重试 |

场景可合并，但至少三组完整输入、实际输出与 Trace，覆盖所有验收点。测试结果保存到 examples/test-results/，评估文档链接到具体文件。

默认离线测试可使用 Mock 和确定性工具。真实模型验证单列，至少跑出两条不同观察驱动的路径；固定 Mock 轨迹不能冒充真实 Agent 决策。

Trace 建议 JSONL，记录 run_id、task_id、模式、步骤、工具参数、返回摘要、状态、累计费用、后续动作、简要依据。不要要求或保存内部思维链，不记录密钥或认证头。
