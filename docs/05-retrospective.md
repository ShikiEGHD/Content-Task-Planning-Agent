## 已知准备问题

G 盘仓库由不同 Windows 账号操作，出现 Git dubious ownership 提示；用户为该具体目录添加信任，并确认 origin 指向指定仓库。该问题不证明 GitHub 推送权限或业务功能已通过验证。

## 问题与处理

已定位的业务问题：费用误读 minutes 字段，估算未含本次估算/保存费；多候选只计算最后一个；工期错误地假设素材检索和脚本生成独立并行；保存只信任旧 feasible；PowerShell 重定向造成 GBK 文件和空错误输出。
处理：集中 accounting.py，显式执行脚本集合和剩余工具费，按真实依赖累计模拟分钟，保存重新校验，--output 原子 UTF-8 写入，固定时钟实际重跑并保留源码/结果哈希。
经验：状态 completed、测试数量和文件存在不足以证明预算/依赖正确；必须用精确边界、真实数据回算和保存前状态变化测试。

## 个人参与与学习收获

本次项目中，我主要负责提出初步想法和方案，与 AI 讨论可行性，并在比较不同框架及实现方法的优缺点后提出建议、作出决策。功能完成后，我参与代码复查和功能测试，将实际运行结果与考核要求对照，反馈问题并配合后续验证。具体实现和修复主要由 AI 辅助完成，详细分工见 [AI 使用与个人贡献](04-ai-usage.md)。

通过这一过程，我加深了对不同框架及其适用场景的了解，也对项目采用的方法形成了初步认识。结合 LangGraph 的节点、状态与路由，我开始理解 Agent 如何围绕“选择动作、执行工具、观察结果、调整下一步”运行；结合云端与 Mock 验证，我认识到流程测试与真实模型行为验证各自承担的作用。

代码复查和测试还帮助我理解了本地持久化与幂等、并发与任务依赖、费用和工期核算，以及 Trace 对问题定位的价值。项目中的计算和编码问题也让我认识到，运行结束或返回 completed 并不足以证明结果正确，还需要核对费用明细、保存内容、约束边界和失败处理。

这些学习使我对项目的整体结构、选型理由和主要方法有了初步理解。后续我计划通过独立实现部分功能、阅读框架文档和复现异常场景，进一步提高代码阅读、调试及验证能力。
